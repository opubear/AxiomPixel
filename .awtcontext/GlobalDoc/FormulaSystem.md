# 构式系统（Formula System）

更新日期：2026-10-14。本文是 AWT 下的系统设计入口，汇总最初的封闭组合想法、整体玩法方案、语言原型和已确认命名。具体语言与实现边界见 [构式语言架构](FormulaLanguageArchitecture.md)，语法及运行命令见 [原型说明](../../Pixel/Formula/README.md)。

## 1. 名称与概念

用户于 2026-10-13 确认，以 **构式（Formula）** 替代“法术”，强调数学构造、程序组合与科幻技术风格。后续设计、讨论和面向玩家的文字统一使用“构式”；“构式语言”是描述这些组合的领域语言。

| 统一术语 | 含义 | 现有代码或历史名称 |
|---|---|---|
| 构式 Formula | 可复用、可组合、可执行的行为描述 | `Formula`；早期提案称 `SpellExpr` |
| 构式系统 Formula System | 从组合、执行到世界反馈的整体玩法 | 法术系统 |
| 构式语言 Formula DSL | 构式的文本描述语言 | `Pixel/Formula`，`.formula` 文件 |
| 激活 / 执行构式 | 接受一次运行请求并启动描述 | `cast`、`Simulator::Cast`、`CastId` |
| 子构式 payload | 事件发生后独立启动的完整构式 | 子法术；`OnHitNode::Payload` |
| 构式运行实例 | 一次激活产生的弹体、调度项与局部状态 | 与不可变 `Formula` 描述区分 |
| 修改器 / 装饰器 | 改变参数 / 增加时间、复制与触发行为 | Modifier / Decorator，名称保留 |

2026-10-14 按用户要求完成代码命名迁移：`Spell` → `Formula`、`pixel::spell` → `pixel::formula`、`Pixel/Spell` → `Pixel/Formula`、`PixelSpell*` → `PixelFormula*`、示例扩展名 `.spell` → `.formula`，测试名同步为 `Pixel.Formula*`。当前头文件入口为 `Formula/Formula.h` 与 `Formula/Simulator.h`，独立构建目录使用 `build-formula`。这次直接迁移原型名称，不提供旧类型、目标或头文件的兼容别名；调用方应更新引用。`cast`、`Simulator::Cast` 与 `CastId` 的激活语义保持不变。

历史任务 ID 和原始 DOCX 保留，以便追溯。执行器、能量等其他科幻设定尚未命名定案。

## 2. 核心玩法与设计目标

构式是本游戏的核心玩法方向。玩家通过“获得基础组件 → 组合与复用 → 执行实验 → 观察环境反馈 → 调整结构”获得新的能力。玩法原型来自 Noita 的组合思路；本项目独立定义组合代数、作用域和调度规则，不承诺复刻其牌堆或内部执行方式。

玩家改变的不只是数值，还包括空间和时间结构：一个弹体可以加速、扩展为一组、延迟启动，或在命中后执行另一套完整构式。泥土、风场和力场为组合提供可观察的环境响应。

优先验证两个问题：玩家能否预测某个修改器影响哪些效果；玩家能否通过改变组合结构得到新行为，并解释其因果。费用、冷却、槽位和风险属于后续玩法取舍，尚不是当前原型规则。

编辑体验有两层：当前文本 DSL 便于验证语义；后续可用槽位、卡牌或可折叠节点组生成同一描述。早期“玩家无需输入代码”的设想仍是 UI 方向，不妨碍以独立语言验证核心结构。是否让玩家直接编写文本尚待试玩决定。

## 3. 封闭组合契约

令 S 为有限、结构良好、参数合法的构式描述集合。基础构造器产生 S 中的值；固定合法参数的修改器与装饰器是 `S → S`；多输入组合器如 `seq`、`on_hit` 接收多个 S，仍返回 S。一个组合的结果因此能继续作为另一个节点的输入。

封闭对象是**行为描述**。正在飞行的弹体、世界事件和已产生的效果指令是执行结果，不承担表达式组合接口。分裂通过描述中的组合节点表达，延迟和触发通过描述中的行为节点表达，不需要把输出类型改成“弹体数组”或“回调函数”。

约定如下：

- 描述不可变，可以共享无环子结构；每次激活独立持有运行状态。复用一个构式不会将修改累积回原件。
- 修改器复合满足函数复合的结合律，通常不满足交换律。伤害 10 先加 5 再乘 2 得到 30，交换顺序得到 25。
- `empty()` 是合法的空构式，是 `seq` 的行为单位元；它是值，不是恒等变换 `Id(s)=s`。
- `seq` 在可观察执行上满足结合律，但分支顺序不能随意交换；世界副作用更不能因结构可重新分组就任意重排。
- 类型与结构封闭不代表所有组合都有有效作用，也不代表无限精度、无限资源或无限递归。非法参数产生错误，不能伪装为空构式。

## 4. 作用域、载体与子构式

修改器作用于当前层的兼容效果，穿过组合、延迟、重复与散射。在 `on_hit(carrier, payload)` 中，它只进入 carrier；payload 是独立子构式，必须显式修改。

| 规则 | 当前原型行为 |
|---|---|
| 伤害、速度修改 | 作用于弹体；按内层到外层执行，对应管道从左到右 |
| 不兼容效果 | 保留原效果并记录诊断，例如给 `wind` 加伤害修改器 |
| 命中载体 | 当前只有弹体；给瞬时风或挖掘加 `on_hit` 不会凭空产生碰撞 |
| 多个载体 | 每个弹体都得到自己的触发；不是“整组只触发一次” |
| 命中继承 | 子构式继承根激活 ID、实际命中位置和入射方向 |
| 不继承的属性 | 载体的伤害、速度修改与其他触发绑定；子构式使用自己的描述 |
| 触发次数 | 当前一次命中消耗整个弹体；其各触发绑定按内层到外层启动 |
| 子构式的闭包 | payload 可以包含新的组合、延迟、修改器或 `on_hit` |

“全部不兼容时禁止激活且不扣费”是早期产品建议。当前原型允许执行并诊断，尚无收费、编辑器或严格模式。owner、team、随机种子、世界代号与预算的继承也是后续方案，不是现有字段。

## 5. 系统分层

```mermaid
flowchart TD
    Input["文本语言 / 未来可视编辑器"] --> Desc["不可变构式描述"]
    Desc --> Runtime["当前：CPU 直接解释与调度"]
    Runtime --> Commands["效果指令、事件、运行快照"]
    Commands --> Trace["当前：CLI 与测试日志"]
    Commands -.未来.-> Adapter["Pixel 玩法适配层"]
    Adapter -.领域操作.-> World["纯 CPU World"]
    World -.碰撞事件.-> Runtime
    Commands -.未来.-> Presentation["渲染拥有的不可变帧快照"]
```

当前实现位于 `Pixel/Formula`，可在没有 Axiom 引擎、窗口和 GPU 的条件下独立构建。World、引擎和渲染尚未依赖该模块。

后续编译器可以在描述与运行时之间产生规范化执行计划、能力信息、费用和上界；当前没有独立字节码、计划缓存、`PlanId` 或成本编译阶段。优化应以原型测量为依据，不因长期架构预先引入完整框架。

## 6. 已验证的贯穿示例

```text
let carrier = bolt() |> speed_mul(1.5) |> damage_add(5);
let impact = seq(wind(8, 120), dig(3), delay(2, bolt(4, 30, 12)));
cast on_hit(carrier, impact) |> fan(3, 10);
```

| 时刻 | 原型可观察行为 |
|---|---|
| tick 0 | 三颗弹体，方向 −10°/0°/+10°，伤害 15，速度 90 格/秒 |
| tick 6，显式注入命中 | 三颗载体消耗，记录命中位置，排入子构式 |
| tick 7 | 每个命中位置产生半径 8、强度 120 的风脉冲指令，以及半径 3 的挖掘指令 |
| tick 9 | 每个命中位置生成伤害 4、速度 30、寿命 12 tick 的弹体 |
| tick 21 | 三颗子弹体寿命到期，未自动触发新的命中 |

这些输出目前是日志与运行状态，未改变游戏地形或风场。命中由 CLI 的 `--hit-at 6` 测试操作提供，不能把示例通过理解为真实碰撞闭环已完成。

早期 DOCX 的简化三发风脉冲示例使用演示费用 `3 × (2 + 1 + 1 + 4) = 24`，不是本原型的收费，也不能直接套用于上面额外包含挖掘、伤害修改和子弹体的程序。

## 7. 与世界接入的后续方案（未实现）

由 Pixel 玩法层消费指令并回传事件，保持 World 为纯 CPU 领域模型：

- `DigArea` 转为明确的材料删除操作，适配现有 `World::RemoveDirt`；弹体保持独立实体，不占用地图 `CellType`。
- `WindImpulse` 适配 `World::AddWindImpulse`。风关闭或覆盖不到时遵守真实风策略行为，不暗中开启风场。
- 弹体自行持有速度与运动参数；风响应通过明确适配读取 `SampleWind`。不能未经单位与模型转换就把 `GetForce` 当作弹体加速度。
- 临时力场需显式来源与结束规则，避免持续累加基础场而无法撤销。材质反应归环境系统，不由每种构式重复实现。
- 高速弹体需要扫掠碰撞，候选按命中时间及稳定标识排序；当前只有解析直线轨迹和外部 `Hit`。
- 渲染消费发布后的独立快照；World 不引入 RHI、shader 或纹理，Draw 不读取实时模拟状态。无需为这一玩法把 Pixel 专用逻辑移入 Axiom。

时钟接入仍需独立设计和验证。现有 `World::Tick` 先调用内部带固定步累加器的 Environment，再以传入 duration 更新角色；原型自身另有 60 Hz 时钟，三者尚未统一。早期提案建议把累加器提升到 World/GameplaySimulation，避免重复累计，并定义输入、环境、角色、弹体、事件和领域命令的固定先后顺序。

未来需明确同 tick 查询快照、命令提交、世界重置与暂停单步契约。原型的“到期优先、命中载荷下一 tick 激活”目前是可执行基准，不能未经评审直接换成旧 DOCX 中的另一套先后规则。

## 8. 费用、执行预算与保存（后续研究，当前不实施）

用户在原型阶段要求优先验证玩法与语言，暂不处理系统安全。以下内容保留为先前讨论的设计方向，不作为本原型完成条件。

**玩法费用**与**计算预算**分别建模。早期提案倾向最坏分支费用一次预付、未触发不退款，根冷却只计算一次；是否采用以及参数需要试玩。组合费用可相加，重复与分裂按激活次数放大，条件取最大分支，触发载荷按兼容载体数与触发次数估计；共享描述不等于共享执行费用。

计算预算如果引入，应覆盖整次根激活及所有后代，不能通过触发或复制创建新预算。需分别衡量生成数量、事件、指令、队列、场采样、地形访问和生命周期。DOCX 内的 128 节点、32 层、256 实例等仅为历史压测起点，既非现行限制，也非已验证性能指标。

正式运行时可增加不可变计划版本、请求去重、带代号的实体句柄、重置时提升 WorldEpoch、无触发清理和受限追踪。配方与节点语义需要版本化；若支持运行中保存，还需保存实体、事件队列和资源状态，不能仅存描述后从头执行。

重放必须固定初始世界、输入 tick、规则版本和需要的随机种子。当前无随机机制、存档或联机；同一构建下的调度一致性测试不能替代跨平台逐位一致性保证。
