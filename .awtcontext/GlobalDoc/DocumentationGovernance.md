## 状态词统一

- **现行**：当前规则或操作入口，必须可回溯到当前代码/配置。标出核对日期及临时、默认关闭等条件。
- **设计提案**：已形成方案，尚未交付；设计任务完成不等于功能完成。
- **兼容**：旧格式仍可读或旧接口仍受支持，但不作为新增内容的默认入口。
- **历史**：已替代的实现、已结束的实验、阶段验收和基准。只证明对应日期/配置，不作为当前操作指南。
- **合并跳转**：正文已由另一地址维护，保留短跳转以兼容旧引用。

“代码存在”“可从原生UI操作”“持久化可用”“本轮测试通过”分别说明。临时会话下可玩的设备不等于默认游戏能跨重启保留；已实现UI不等于装备规则已交付。

## 每次功能变更的收尾

1. 先确定所属系统与玩家可观察变化；跨系统改动列出受影响系统，避免只在任务日志留下知识。
2. 更新唯一的现行规则/实现正文：入口、默认值、限制、单位、身份、暂停/卸载/保存、失败结果与兼容范围；无需重复不受影响的字段。
3. 更新相应系统页的“已实现/未交付”与导航；只有跨系统阶段或范围变化才更新 ProductStatus。
4. 用 AWT `doc add` 新增正文、`doc index` 更新已有地址的标题和描述。索引标题带分类，描述含状态；描述单行且不超过80字。
5. 若旧正文被完全替代，先确认独有决策和验证材料已保留，再改为跳转；只部分过时则修订现行段，把旧数据明确标为历史。
6. 核对本地链接、索引地址与唯一性，执行 `git diff --check`。有任务时把实际验证与限制写回该任务，不把旧测试数字改成新结果。

纯共享文档维护无需新建任务；持续开发按工程任务流程记录。不得手改 Task.md 受管区或结构化状态；整理文档不删除任务、需求、验收或反馈。

## 过期资料处理

| 情形 | 处理方式 |
| --- | --- |
| 同一正文的副本 | 保留唯一正文，其余改短跳转；不继续双份更新 |
| 已删除原型与旧按键/旧目录 | 从现行阅读路径移除；历史页首注明替代地址，旧代码链接视为当时证据 |
| 部分过时的现行合同 | 直接修正现行段；历史测试区保留日期、环境和限制 |
| 基准原始数据、审查与阶段验收 | 保留原值，归“证据/历史”；不以旧通过记录代表当前分支 |
| DOCX/PDF原始提案与外部讨论 | 保留来源语境，以索引标明历史/参考；当前规则维护在Markdown合同 |
| 原件/许可/生成记录 | 保留资产来源链；下载清单不等于运行时已使用，原件存在也不等于已纳入Git分发 |
| 引用不存在 | 修正为可用地址；无法恢复的条目标记待补，不用猜测内容或许可 |

历史资料保留原路径并归档分类。本轮不删除有独立来源价值的历史原文；清理对象是失效的现行说法、重复正文和误导性索引状态。

## 职责与核查触发

- 玩法/内容变更：对应系统实现者负责更新系统入口与规则，策划复核体验目标、数值与未交付项。
- 架构/保存/单位变更：实现者核对所有受影响系统；项目管理复核兼容范围、默认开关和验收边界。
- 素材变更：内容接入者同时维护原件来源、清单、运行时使用关系和安装/恢复方式。
- 每个功能任务完成、阶段验收、正式试玩前执行一次受影响文档核查；发现矛盾当批修订。此规则不创建定时任务或后台自动维护。

AWT DocIndex 是工具生成的三列表，统一使用“总览 / 系统 / 工程 / 资源 / 证据 / 历史”标题前缀；分层阅读结构由稳定的策划入口承载，不依赖工具保留表格分组或第四状态列。
